# refueling-during-the-flight
Тестовое задание

- **Пункт 1. Расхождения**

| № | Расхождение | Решение | Причина такого решения |
|---|---|---|---|
| 1 | В макете и разговоре с диспетчером общий лимит 20 000 ₽, а в API — 15 000 ₽. | Согласовать общий лимит. В fake-api изменить limitTotal в getTrip() на утверждённое значение. В интерфейсе получать лимит из API. | Водитель должен видеть достоверный лимит, иначе возникает недоверие к приложению. |
| 2 | В макете доступно 12 450 ₽, в API — 9 340 ₽, а диспетчер говорит примерно о 9 300 ₽. | В fake-api согласовать начальное значение limitLeft с бизнес-данными. В интерфейсе показывать значение из getTrip(), а не фиксированную сумму. | Водитель должен знать, сколько денег реально доступно для заправки. |
| 3 | Диспетчер объясняет уменьшение лимита заправкой на 5 600 ₽ и временным холдом. В API и макете нет подробной информации. | В fake-api расширить getTrip() полями spentAmount и heldAmount, добавить историю операций и сроки снятия блокировок. В интерфейсе показать детализацию лимита. | Водитель сможет самостоятельно разобраться в остатке без звонка диспетчеру. |
| 4 | Диспетчер разрешает отмену до 50% налива, а API — только до начала налива. | Согласовать правило отмены. В fake-api изменить cancelFueling() для поддержки отмены до 50%, если это подтверждено бизнесом, и рассчитывать фактическое списание. В интерфейсе показывать отмену только когда она разрешена. | Инструкция диспетчера должна соответствовать техническим возможностям приложения. |
| 5 | Диспетчер говорит о 40 секундах ожидания пистолета, а в API тайм-аут равен 60 секундам от создания заказа. | В fake-api согласовать тайм-аут в progress() и добавить время его окончания в getFueling(). В интерфейсе показывать обратный отсчёт. | Водитель должен понимать, сколько времени осталось до отмены заказа. |
| 6 | На АЗС «Колесо» колонки обозначены буквами А, Б, В, Г, а API возвращает номера. | В fake-api добавить к колонкам поле displayName, сохранив number. В интерфейсе показывать обозначения с реальной АЗС. | Водитель не должен самостоятельно переводить буквы в цифры и рисковать выбором неправильной колонки. |
| 7 | Макет сообщает, что чек отправлен диспетчеру, но диспетчер получает его позже. В API нет данных о чеке. | В fake-api добавить receiptStatus и при необходимости метод получения чека. В интерфейсе показывать подтверждённый статус, например «Ожидаем чек от АЗС». | Нельзя сообщать об отправке чека, если она не подтверждена. |
| 8 | В макете есть номер прицепа, а getTrip() возвращает только номер тягача. | В fake-api добавить в getTrip() поле trailer при наличии данных. В интерфейсе получать номер прицепа из API. | Информация о транспорте должна соответствовать текущему рейсу. |
| 9 | Диспетчер говорит об ограничении 150 л на «Колесе». В API оно есть, но соответствующий экран в макете отсутствует. | В fake-api оставить существующие litersMin и litersMax в getStation(). В интерфейсе показывать диапазон и ограничивать ввод. | Водитель должен видеть ограничения до оформления заказа. |
| 10 | При потере связи водитель может отправить заказ повторно. В API есть clientRequestId, но нет поиска заказа по этому идентификатору. | В fake-api добавить получение заправки по clientRequestId, сохранив защиту от повторного создания. В интерфейсе сохранять идентификатор, предотвращать повторный заказ и восстанавливать состояние. | Это предотвращает двойные заказы и повторную блокировку лимита. |
| 11 | Макет показывает только успешную заправку, а API предусматривает частичный налив, отмену, тайм-аут и отказ АЗС. | В fake-api использовать существующие статусы и при необходимости добавить признак частичного налива. В интерфейсе разработать состояния ожидания, ошибки, отмены и частичного завершения. | Водитель должен понимать результат заправки даже при возникновении проблемы. |
| 12 | Диспетчер говорит, что рефрижератор заправляется отдельным заказом, но API не различает баки. | В fake-api добавить в startFueling() параметр equipmentType со значениями truck и refrigerator и сохранять его в заказе. В интерфейсе добавить выбор оборудования. | История операций должна показывать, что именно заправлялось, при общем лимите. |
| 13 | В макете нет промежуточных экранов, хотя API различает подтверждение, ожидание пистолета и налив. | В fake-api использовать существующий getFueling() без обязательных изменений. В интерфейсе отображать этап процесса в зависимости от статуса. | Водитель должен понимать, принято ли распоряжение и какие действия нужны дальше. |
| 14 | На табло АЗС цена 71,70 ₽, а в приложении 71,71 ₽. API может отклонить заказ при изменении цены. | В fake-api сохранить PRICE_CHANGED и передачу новой цены, согласовать правила округления. В интерфейсе показывать актуальную цену и запрашивать повторное подтверждение при изменении. | Водитель должен знать цену, по которой фактически оформляется заказ. |
| 15 | После потери связи или закрытия приложения заправка может продолжаться, но восстановление не показано в макете. | В fake-api использовать getActiveFueling() и добавить поиск заказа по идентификатору независимо от статуса. В интерфейсе восстанавливать текущую операцию при запуске. | Водитель не должен терять информацию о заказе и создавать новый по ошибке. |
| 16 | API резервирует полную сумму заказа и затем возвращает неиспользованную часть, но макет этого не объясняет. | В fake-api использовать amountHeld и при необходимости добавить общий активный резерв. В интерфейсе отдельно показывать заблокированные средства и фактическое списание. | Водитель должен понимать, почему доступный лимит уменьшился до завершения заправки. |
| 17 | Макет показывает фиксированные литры и сумму, а API допускает завершение с меньшим фактическим объёмом. | В fake-api использовать factLiters и factAmount; при необходимости добавить признак частичной заправки. В интерфейсе показывать фактический объём, стоимость и разницу с заказом. | Водитель должен видеть реальные результаты и корректную сумму списания. |
| 18 | getStations() возвращает 300 АЗС в перемешанном порядке, а водителю нужны ближайшие подходящие станции. | В fake-api при необходимости добавить поиск АЗС по координатам. Для прототипа использовать getDriverLocation() и getStations(), сортируя список на стороне приложения. | Водитель сможет быстрее выбрать подходящую АЗС без просмотра всего списка. |
